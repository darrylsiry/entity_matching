================================================================================
ENTITY MATCHING — HOW THE MATCHING WORKS (plain-English reference)
================================================================================

This document describes, in order, what the matching engine does, which
open-source tools each step uses, and every parameter/threshold that is set.
It reflects the code in backend/app/matching/ (pipeline, normalize, deterministic,
probabilistic, fuzzy, embedding, scoring, cluster, dedupe).

There are TWO modes. They share the same steps; the only differences are what gets
compared and how the final answer is shaped:

  • LINK MODE ("compare two files")  — match rows of File A against File B.
      Output: matched pairs (A <-> B) classified as Match or Review, with everything
      else reported as "unique" (unmatched).

  • DEDUPE MODE ("deduplicate one file") — find duplicate rows within one file.
      Output: every row gets a "master ID"; rows sharing a master ID are the same
      company.

The core idea is a CASCADE (a waterfall): run the strongest, most certain method
first, remove whatever it confidently resolves, then run the next method only on
what's left. Cheap/strict methods handle the easy cases; fuzzier methods handle the
leftovers. "Blocking" (only comparing records that share some signal) is what keeps
it fast enough for 100k+ rows without comparing every possible pair.


--------------------------------------------------------------------------------
CANONICAL FIELDS
--------------------------------------------------------------------------------
Uploaded files can have any column names. During "Map columns" (link mode) or
auto-detection (dedupe mode) each source column is mapped to one of these canonical
fields. Everything downstream speaks in these names:

  name            (REQUIRED)   company / legal name
  registration_id              DUNS / EIN / VAT / company number (an optional per-file
                               "id type" declaration prevents cross-type collisions)
  website                      URL or email (a domain is extracted from it)
  phone                        normalized internationally (E.164)
  address                      street address
  city, state, postcode, country


--------------------------------------------------------------------------------
STAGE 0 — NORMALIZE   (always runs first)
--------------------------------------------------------------------------------
Turns messy raw values into clean, comparable forms so trivial formatting
differences don't block a match.  File: normalize.py

Tools: cleanco (strips legal suffixes), tldextract (domain parsing, offline/pinned
suffix list), Unidecode (accent folding), pycountry (country resolution),
phonenumbers (phone parsing), jellyfish (metaphone), postal/libpostal (address
parsing — OPTIONAL, auto-fallback when not installed), pandas.

What it does per field:
  • name:
      - Unicode-fold (Café -> cafe), lowercase, trim; "&"/"+" become "and".
      - Strip corporate/legal suffixes via cleanco (Inc, LLC, Ltd, GmbH, Corp, ...).
      - Expand common abbreviations token-wise (Intl -> international, Mfg ->
        manufacturing, Svcs -> services, Grp -> group, Tech -> technology, ...) and
        drop a leading "the" — so "The Acme Intl Grp" == "Acme International Group".
      - Remove punctuation, collapse whitespace.
      - Also derive a "name tokens" key = the unique words sorted alphabetically
        (so "Acme Global" and "Global Acme" produce the same key). Used for blocking.
      - Also derive METAPHONE codes per token ("johnson" and "jonson" -> JNSN), used
        as additional blocking keys so typos in the first letters still compare.
  • website -> domain:
      - Extract the registrable domain from a URL or email
        ("https://www.Acme.com/about" and "jane@acme.com" both -> "acme.com").
      - GUARD: generic/shared domains are dropped to "" (treated as no signal),
        because many unrelated companies share them. Blocklist includes free email
        (gmail.com, yahoo.com, outlook.com, hotmail.com, icloud.com, aol.com, ...),
        social (linkedin.com, facebook.com, x.com/twitter, instagram, youtube),
        and site-builders/hosting (wix, squarespace, weebly, godaddy, wordpress,
        shopify, blogspot), plus example.com/test.com.
  • registration_id:
      - Keep alphanumerics only, lowercase.
      - GUARD: return "" (no signal) for placeholders ("N/A", "none", "null", "tbd",
        "unknown", "test", ...), for values shorter than 4 characters, or for a single
        repeated character ("0000", "aaaa").
  • phone:
      - Parsed with a country hint (default US) and normalized to E.164, so
        "(415) 867-5309" == "+1 415-867-5309" == "+14158675309".
      - GUARD: return "" for invalid numbers, placeholders (555-555-..., 123-456-7890),
        fewer than 7 digits, or all-same-digit values.
  • country: resolved to ISO 3166-1 alpha-2 ("USA", "U.S.A.", "United States" -> "us");
      unresolvable values pass through cleaned (signal is never dropped).
  • state: US states + Canadian provinces mapped to postal codes ("California" ->
      "ca"); other regions pass through cleaned.
  • address: punctuation-stripped, whitespace-collapsed — then one of two modes
      (which mode is active is logged once at startup):
      - WITH libpostal installed (optional; ~2 GB C-library, see the README): each
        address is PARSED into components (house number, road, unit, city, state,
        postcode). The road is run through libpostal's expansion so "Main St" ==
        "Main Street". Two derived columns (house number, road) feed Stages 2–3.
        If the file has NO separate city/state/postcode column mapped, those are
        BACKFILLED from the parse (user-mapped columns are never overwritten).
      - WITHOUT libpostal (the default install): a built-in abbreviation table is
        applied token-wise to the whole string (St -> street, Ave -> avenue,
        Blvd -> boulevard, Ste -> suite, Apt -> apartment, N/S/E/W -> north/...),
        so "123 Main St Ste 4" == "123 Main Street Suite 4".
  • city: punctuation-stripped, whitespace-collapsed.
  • postcode: alphanumerics only ("SW1A 1AA" -> "sw1a1aa").


--------------------------------------------------------------------------------
STAGE 1 — DETERMINISTIC (exact identifier match)   [strongest, runs first]
--------------------------------------------------------------------------------
Exact joins on near-certain identifiers.  File: deterministic.py   Tool: pandas.

Order of keys (highest priority first); empty/guarded values are ignored:
  1. registration_id  (exact, normalized)
  2. website domain    (exact, normalized)
  3. phone number      (exact, E.164)

ID-TYPE GUARD: if both files declare a registration-id *type* (DUNS/EIN/VAT/...) and
they differ, the id key is skipped entirely — a DUNS in file A that numerically
collides with an EIN in file B is not a match. "unknown" on either side joins as
before.

CORROBORATION GUARD (domain and phone only — never registration_id): subsidiaries,
franchises, and portfolio companies share websites and switchboards, so a shared
domain/phone alone is strong but not conclusive. For each domain/phone-only pair the
fuzzy name similarity is checked:
  • name similarity >= 0.30  -> emit at 0.99  (rule "domain+name_ok" / "phone+name_ok")
  • name similarity <  0.30  -> DEMOTE to 0.80 (the review band; rule
    "domain_name_conflict" / "phone_name_conflict") and keep the records in the pool
    for later stages. A human decides.
A pair that ALSO matches on registration_id bypasses the guard (always 0.99).

Only pairs at/above the Match threshold are removed from the pool before the
probabilistic stage runs; demoted pairs stay in play.

  Parameters:  DETERMINISTIC_SCORE = 0.99, deterministic_corroboration = true,
               deterministic_name_floor = 0.30, deterministic_demoted_score = 0.80


--------------------------------------------------------------------------------
STAGE 2 — PROBABILISTIC (Splink / Fellegi–Sunter)   [runs on the leftovers]
--------------------------------------------------------------------------------
The scalable workhorse. Instead of comparing all pairs, it uses BLOCKING to generate
only plausible candidate pairs, then scores each with a probabilistic model over
several field comparisons.  File: probabilistic.py
Tool: Splink 4 on a DuckDB backend.

Runs only on records NOT already resolved by Stage 1.
  • Link mode:  link_type = "link_only"   (only cross-file A<->B pairs)
  • Dedupe mode: link_type = "dedupe_only" (within-file pairs)

BLOCKING RULES (a pair is considered only if it shares at least one of these; each key
is wrapped so that EMPTY values are NOT joined — this is important, otherwise every
blank-website row would be lumped together and mis-scored):
  • name tokens (the sorted-words key)
  • postcode
  • website domain
  • phone (E.164)
  • first-name-token METAPHONE (phonetic — survives typos in the first letters)
  (If none of those carry signal, it falls back to blocking on the first 4 characters
   of the name.)

FIELD COMPARISONS used to score a candidate pair (only fields present in the data):
  • name      — Jaro-Winkler at thresholds [0.9, 0.8], with TERM-FREQUENCY adjustments
                (agreement on a rare name counts for more than on a common one)
  • domain    — exact match
  • phone     — exact match
  • address   — with libpostal parses available: house number exact match + road
                Levenshtein at thresholds [2, 5] (so a missing "Ste 4" no longer
                reads as disagreement); otherwise the whole normalized string,
                Levenshtein at thresholds [2, 5]
  • postcode  — exact match
  • city      — exact match, with term-frequency adjustments

MODEL TRAINING (unsupervised — no labelled data needed):
  • estimate_probability_two_random_records_match(recall = 0.7)
  • estimate_u_using_random_sampling(max_pairs = 1,000,000)
  • Expectation-Maximisation (EM) run once per blocking rule to learn "m" values.

PREDICTION:
  • Emit pairs with match_probability >= probabilistic_threshold (default 0.75).
  • A probabilistic pair scoring >= the MATCH threshold (0.90) is treated as
    confidently resolved and removed before the fuzzy stage; weaker ones are left in
    so the fuzzy stage can still weigh in.

Robustness: the entire Splink stage is defensive — if Splink isn't installed or EM
fails to converge on small/low-variety data, it logs a warning and returns nothing,
and the pipeline falls back to the fuzzy stage rather than crashing.


--------------------------------------------------------------------------------
STAGE 3 — FUZZY FALLBACK (rapidfuzz)   [runs on whatever is still unresolved]
--------------------------------------------------------------------------------
Catches remaining matches by name similarity.  File: fuzzy.py   Tool: rapidfuzz.

BLOCKING: each record contributes one key per name word = that word's first 4
characters, PLUS (when phonetic blocking is on) each word's METAPHONE code, so
"Jonson" and "Johnson" (different prefixes, same code JNSN) still get compared. Two
records are compared if they share ANY key. This tolerates word-order differences and
typos anywhere in the word while keeping the comparison count low.
  Parameters:  _PREFIX_LEN = 4, use_phonetic_blocking = true

NAME SIMILARITY METRIC (0..1):
  score = min( token_sort_ratio , token_set_ratio )
  We deliberately take the MINIMUM of the two rather than token_set_ratio alone.
  token_set_ratio returns 1.0 whenever one name's words are a subset of the other's
  ("Apple" vs "Apple Bank for Savings" -> 1.0), which caused false positives;
  token_sort_ratio has no such subset leniency, so the min keeps genuine matches and
  typos high while collapsing subset coincidences.

CORROBORATION / CONFLICT ADJUSTMENT (applied to the name score using other fields;
missing fields never penalize):
  • address: compared with token_set_ratio — on "house number + road" when libpostal
    parsed them (unit/suite noise ignored), else on the whole normalized string.
      - similar   (>= 0.70):  +0.05   (agreement raises confidence)
      - conflicting (< 0.45): -0.18   (clearly different address pushes a name-only
                                       coincidence DOWN, into the review band instead
                                       of auto-matching)
  • same city:      +0.03
  • same postcode:  +0.03
  • same state:     +0.03   (compared on postal codes: "California" == "CA")
  • same country:   +0.03   (compared on ISO codes: "USA" == "United States")
  Final score is clamped to [0, 1].
  PROVENANCE: every applied adjustment is recorded on the pair (e.g.
  "same_postcode,addr_agree") and shown to reviewers as chips, so they can see WHY a
  score is what it is.
    Parameters:  _ADDR_AGREE = +0.05,  _ADDR_CONFLICT = -0.18,  _FIELD_AGREE = +0.03

EMIT:
  • Link mode: for each A record, keep only its single BEST B match whose adjusted
    score is >= fuzzy_threshold (default 0.80).
  • Dedupe mode: emit every within-file pair >= fuzzy_threshold (so multi-row
    duplicate groups link up fully).


--------------------------------------------------------------------------------
STAGE 3.5 — SEMANTIC / EMBEDDINGS (optional, OFF by default)
--------------------------------------------------------------------------------
Catches matches no string metric can see: "IBM" vs "International Business
Machines", "VW" vs "Volkswagen" — acronyms, expansions, trade vs legal names.
File: embedding.py   Tools: sentence-transformers (model all-MiniLM-L6-v2, runs
locally on CPU — no API calls), hnswlib for approximate search above ~20k rows
(exact numpy search below that). Both dependencies are optional: if the stage is
enabled but they aren't installed, it logs a warning and is skipped.

Runs ONLY on residuals — records that appear in NO pair from any earlier stage —
so it can only add candidates nothing else found.

HOW: each residual record becomes the text "name, city, country" (empty parts
skipped) and is embedded into a vector; records whose vectors are close in meaning
get high cosine similarity even when the spellings share nothing.
  • Link mode: file B residuals are indexed; each A residual queries its top 5
    nearest neighbors; pairs with cosine >= embedding_threshold (0.85) become
    candidates, best-per-A kept.
  • Dedupe mode: all residual rows are indexed; every within-file pair above the
    threshold is emitted.

GUARDRAILS (embeddings also consider same-industry names "similar", e.g. two
different airlines — so this stage is deliberately distrusted):
  • The fuzzy stage's corroboration adjustments apply first (address +-0.05/-0.18,
    city/postcode/state/country +0.03), recorded as provenance.
  • A pair with NO exact city or postcode agreement is CAPPED at 0.89 — just below
    the default 0.90 match threshold — so on its own it can only ever land in the
    REVIEW queue, never auto-match. A human (or LLM adjudicator) decides.
  • Exact city or postcode agreement lifts the cap (score = adjusted cosine).

  Parameters:  use_embedding = false, embedding_threshold = 0.85,
               embedding_model = "all-MiniLM-L6-v2", top-k = 5, review cap = 0.89


--------------------------------------------------------------------------------
STAGE 4 — RESOLVE (combine + classify)
--------------------------------------------------------------------------------
File: scoring.py (link) / cluster.py + dedupe.py (dedupe).

LINK MODE — classify each pair by its score into bands:
  • score >= 0.90  -> MATCH   (auto-accepted)
  • score >= 0.75  -> REVIEW  (uncertain; surfaced for a human decision)
  • score <  0.75  -> dropped (no match)
  Each A record keeps only its single highest-scoring pair (deterministic 0.99 hits
  naturally win). Every A and B row that ends up in no Match/Review pair is reported
  as "unique" (unmatched), so the categories reconcile:
      per file:  matched + review + unique  =  total rows.
  PER-STAGE OVERRIDES: because scores from different stages sit on different scales,
  the thresholds can optionally be overridden per stage (e.g. a stricter match bar for
  fuzzy pairs only) via stage_thresholds; unset values inherit the globals.
  RE-CLASSIFY WITHOUT RE-RUNNING: every stage-emitted pair is also stored, so changing
  the thresholds afterwards only re-runs this classification step (instant) — the
  Results screen has a Thresholds panel for exactly this.
    Parameters:  match threshold = 0.90,  review threshold = 0.75,
                 stage_thresholds = null (inherit)

DEDUPE MODE — cluster instead of classify (same confidence split as link mode):
  Links from Stages 1–3 are split by score:
    • CONFIDENT links (score >= 0.90) are pooled and connected-components are computed
      with a union-find (disjoint-set) algorithm. Each group becomes one entity with a
      master ID (numbered by smallest row index, so IDs are stable). Unlinked rows are
      singletons.
    • REVIEW-band links (0.75 <= score < 0.90) that would join two *different* clusters
      are NOT merged automatically. They become "possible duplicates" — surfaced for the
      user to confirm (which merges the two rows' clusters) or dismiss (keeps them
      apart). See the review workflow below.


--------------------------------------------------------------------------------
HUMAN REVIEW WORKFLOW
--------------------------------------------------------------------------------
LINK MODE (review.py). For every pair classified as REVIEW the user can:
  • Confirm  -> it becomes a MATCH in the final dataset (and CSV export).
  • Dismiss  -> it is not a match; the two records revert to "unique".
  • Undo     -> clears a prior decision.

DEDUPE MODE (dedupe_review.py). For every "possible duplicate" candidate the user can:
  • Confirm  -> the two rows merge into the same master ID (clusters recomputed).
  • Dismiss  -> the rows stay in separate clusters.
  • Undo     -> clears a prior decision.

In both modes decisions are stored as a small overlay and applied when results/counts/
CSV are read, so the exported dataset always reflects the user's choices.

Review efficiency (link mode): pairs can be decided in BULK ("Confirm all"/"Dismiss
all" on the current view) or by KEYBOARD (↑/↓ or j/k navigate, y confirm, n dismiss,
u undo). Every pair shows its provenance — the stage/rule that produced it and the
corroboration chips — so a reviewer sees why it scored what it did.

EVALUATION (link mode): upload a labeled sample of true matches (columns
file_a_name,file_b_name) and the Results screen scores the current match set
(precision / recall / F1) and sweeps the stored pair scores to SUGGEST the
best-F1 match threshold, which can be applied with one click.


--------------------------------------------------------------------------------
ALL TUNABLE PARAMETERS AND THEIR DEFAULTS
--------------------------------------------------------------------------------
Set on the "Configure" step (SessionConfig) — user-adjustable per run:
  use_deterministic          = true      turn Stage 1 on/off
  use_probabilistic          = true      turn Stage 2 (Splink) on/off
  use_fuzzy                  = true      turn Stage 3 on/off
  thresholds.match           = 0.90      score at/above this = Match
  thresholds.review          = 0.75      score at/above this = Review (else dropped)
  fuzzy_threshold            = 0.80      min adjusted score for the fuzzy stage to emit
  probabilistic_threshold    = 0.75      min Splink probability to emit a pair
  use_phone                  = true      phone as identifier (needs a mapped column)
  default_phone_region       = "US"      country hint for numbers without a code
  use_phonetic_blocking      = true      metaphone blocking keys (recall only)
  splink_tf_adjustments      = true      rare-name/rare-city weighting
  deterministic_corroboration= true      name-sanity guard on domain/phone matches
  deterministic_name_floor   = 0.30      name similarity below this -> demote
  deterministic_demoted_score= 0.80      demoted pairs land here (review band)
  stage_thresholds           = null      optional per-stage match/review overrides
  registration_id_type_a/_b  = unknown   declared id type per file (session-level)
  use_libpostal              = true      structured address parsing (auto-falls back
                                         to abbreviation expansion if not installed)
  use_embedding              = false     semantic Stage 3.5 on residuals (needs
                                         sentence-transformers installed)
  embedding_threshold        = 0.85      min cosine similarity for a candidate
  embedding_model            = "all-MiniLM-L6-v2"   local sentence-transformer

Fixed in code (not exposed in the UI):
  Deterministic score                = 0.99
  Deterministic key order            = registration_id, domain, phone
  Registration-id guard              = drop if placeholder, < 4 chars, or all-same-char
  Phone guard                        = drop if invalid, < 7 digits, placeholder ranges
  Generic-domain blocklist           = free email / social / site-builders (dropped)
  Name abbreviation table            = intl/natl/mfg/svcs/grp/tech/... expanded
  Address abbreviation table         = st/ave/rd/blvd/ste/apt/n/s/e/w/... expanded
                                       (the no-libpostal fallback)
  Fuzzy blocking keys                = first 4 chars + metaphone code of each name word
  Fuzzy name metric                  = min(token_sort_ratio, token_set_ratio)
  Fuzzy address agree / conflict     = +0.05 (sim >= 0.70) / -0.18 (sim < 0.45)
  Fuzzy city/postcode/state/country  = +0.03 each on exact (normalized) agreement
  Splink blocking keys               = name tokens, postcode, domain, phone,
                                       first-token metaphone (empties excluded)
  Splink name comparison             = Jaro-Winkler thresholds [0.9, 0.8] (+TF)
  Splink address comparison          = Levenshtein thresholds [2, 5] (on the parsed
                                       road + exact house number when available)
  Splink domain/phone/postcode       = exact match; city exact (+TF)
  Splink u-training sample size      = 1,000,000 random pairs
  Splink probability-two-match recall= 0.7
  Embedding review cap               = 0.89 (lifted only on exact city/postcode
                                       agreement); top-k neighbors = 5
  Upload limits                      = 100 MB / 500,000 rows per file

TOOLS AT A GLANCE
--------------------------------------------------------------------------------
  pandas        data handling throughout; exact joins for Stage 1
  cleanco       strip legal/corporate name suffixes
  tldextract    extract registrable domain from URLs/emails
  Unidecode     fold accents to ASCII
  pycountry     resolve country names/codes to ISO 3166-1 alpha-2
  phonenumbers  parse/validate phone numbers to E.164
  jellyfish     metaphone codes for phonetic blocking
  postal        libpostal binding — structured address parsing (optional install;
                falls back to a built-in abbreviation table when absent)
  sentence-transformers  local embedding model for the semantic stage (optional;
                stage skipped with a warning when absent)
  hnswlib       approximate nearest-neighbor index for embeddings at scale
                (optional; exact numpy search used below ~20k rows / when absent)
  Splink 4      probabilistic record linkage (Fellegi–Sunter), term-freq adjustments
  DuckDB        embedded columnar engine Splink runs on
  rapidfuzz     fast fuzzy string similarity (token_sort / token_set / Jaro-Winkler)
  union-find    connected-components clustering for single-file dedupe (hand-rolled)
